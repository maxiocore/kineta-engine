- Admin infrastructure E2E tests run only through supabase/functions/cloud-e2e-test (Phase 2 lifecycle: cloud-advanced-test, same rules, stops on first failure) with hard-coded parameters, an atomic one-shot create claim and AES-encrypted SSH keys readable only server-side; why: billable tests never reuse customer paths or the global gate.
- Customer E2E provisioning tests run only through supabase/functions/cloud-customer-e2e using the admin's own session for customer steps, a single-use cloud_e2e_customer_grants row for hidden plans, and an is_e2e_test order flag as the only scoped bypass of LIVE_PROVISIONING_ENABLED; why: the real customer path is tested without opening plans or live provisioning to anyone else.
- The real-provider lifecycle test runs only through supabase/functions/cloud-lifecycle-real-test (fixed CX23/fsn1 params, one atomic create claim, is_lifecycle_test subscription with simulated wallet and no customer emails) and drives the shared engine in _shared/cloud-lifecycle-core.ts; why: real power/delete/backup actions are proven on one test VPS without opening global switches or touching real wallets.
- Suspension power-off is a graceful shutdown first, hard power-off only as fallback (RealProvider in _shared/cloud-lifecycle-core.ts); why: hard power cuts corrupted SSH host keys on an earlier test server.
- Paid cloud orders are provisioned only by the shared engine in _shared/cloud-provisioning-core.ts (automatic queue cloud-provisioning-worker; admin_provision is recovery only) with DB-enforced transitions via cloud_set_provisioning_state, label lookup/adoption before any create, and first-boot readiness before active; why: one provider server per order and no active or refunded order with an unproven state.
- Cloud launch capacity is reserved via _cloud_reserve_launch_slot under a global advisory lock before order_cloud_server charges the wallet through _wallet_post; why: concurrent customers can never exceed the launch limit or be charged without a slot.
- Cloud servers get a DB-generated hostname (srv-<id>) and access_method auto|ssh_key; auto access uses a per-server random root password stored encrypted in service-role-only cloud_server_credentials, revealed once to the owner via cloud-api reveal_credentials then wiped; why: non-technical customers can buy without SSH, and secrets never reach logs, email or admins.
